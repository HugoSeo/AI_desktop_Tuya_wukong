TEF 表情动画格式 · 技术规范

TEF（Tuya Emotion Format） 是一种面向嵌入式小屏设备的表情动画文件格式。它与 GIF 类似——定义了一套"调色板 + 帧序列 + 帧间差分"的动画表达模式——但针对嵌入式设备的解码算力、内存与显示带宽做了重新设计。目标:在存储、CPU、RAM、显示带宽四个维度上同时优于 GIF 与同类嵌入式方案(如乐鑫 EAF),并对表情类素材保持无损。

本规范定义 TEF 的数据格式,并详细描述编码与解码的完整过程及各环节技术选型。

1. 概述

1.1 TEF 是什么

TEF 是一种离线转码、设备端播放的表情动画格式:

  • 离线:主机端编码器把源动画(当前支持 GIF)转换为 .tef 文件;
  • 设备端:解码器解析 .tef,逐帧产出可直接经 SPI / QSPI / RGB 等接口刷到屏幕的像素数据。

核心表达模式:把动画视为"一张全局调色板 + 一串帧",每帧只记录相对上一帧变化的区域(脏块),并对该区域按内容选择最省的编码方式(调色板索引压缩 或 JPEG)。

1.2 设计目标(按优先级)

  1. 运行时最省:CPU、RAM、显示带宽尽量低。
  2. 存储不吃亏:表情类素材体积显著小于 GIF;写实类素材提供 JPEG 路径兜底。
  3. 画质无损:表情类(少色、色块)做到 bit-exact;写实类允许有损。
  4. 单一容器通吃:一个格式同时承载"色块表情"与"写实过场",解码器按帧自动分派。

2. 设计原理

TEF 由五个机制协同,这是它同时赢下多个维度的根本原因。

机制 作用 主要收益维度
块级帧间差分:帧切成 tile 网格,只记录/解码/刷新变化的 tile 跳过未变区域 存储·CPU·带宽
全局调色板 + 位深自适应(1/4/8bit) 按色数把索引压到最小 存储·RAM
自适应 tile 尺寸 编码时扫描最优 tile,平衡脏块粒度与元数据开销 存储

3. 数据格式规范

3.1 约定

  • 多字节字段采用小端序。
  • 像素输出为 RGB565(默认)或 RGB888(可选),bpp 为每像素字节数。
  • 坐标原点为画布左上角。
  • n_tiles = ceil(canvas_w / tile_w) × ceil(canvas_h / tile_h),边缘 tile 按画布裁剪。

3.2 总体布局

偏移              内容
0                 文件头 tef_header (32 字节)
palette_off       全局调色板    ncolors × u16 (RGB565)
...               段负载 0 / 1 / ...(调色板段或 JPEG 段)
seg_table_off     段表          seg_count × tef_seg (每段 16 字节)

TEF 以段(segment)为组织单位。一个段覆盖一段连续帧,分两类:调色板段(一段连续的色块帧,合并为一条压缩流)或 JPEG 段(单个写实帧)。

3.3 文件头

struct tef_header {          // 32 字节,小端
    char     magic[4];       // "TEF1"
    uint16_t version;        // 1
    uint16_t canvas_w;       // 画布宽
    uint16_t canvas_h;       // 画布高
    uint8_t  tile_w;         // tile 宽(编码时自适应选定)
    uint8_t  tile_h;         // tile 高
    uint16_t frame_count;    // 帧数
    uint16_t fps;            // 默认帧率
    uint16_t ncolors;        // 全局调色板色数(≤256;纯 JPEG 素材可为 0)
    uint8_t  index_bits;     // 索引位深:1 / 4 / 8
    uint8_t  flags;          // bit0: 输出 RGB888(否则 RGB565)
    uint16_t seg_count;      // 段数量
    uint16_t _pad;
    uint32_t palette_off;    // 全局调色板偏移
    uint32_t seg_table_off;  // 段表偏移
};

3.4 全局调色板

ncolors 个 uint16 RGB565 颜色,整段动画共享,只存一次。位深由色数自动决定:≤2 色 → 1bit,≤16 色 → 4bit,≤256 色 → 8bit。

3.5 段表项

struct tef_seg {             // 16 字节
    uint8_t  method;         // 0 = 调色板段, 1 = JPEG 段
    uint8_t  comp;           // 调色板段:0=heatshrink,1=deflate;JPEG 段忽略
    uint16_t frame_start;    // 本段起始帧号
    uint16_t frame_count;    // 本段覆盖帧数
    uint16_t _r;
    uint32_t offset;         // 段负载文件偏移
    uint32_t comp_len;       // 段负载字节数
};

3.6 调色板段负载(method = 0)

段负载是一条熵编码流(heatshrink 或 deflate)。解压后得到一个原始 blob,按帧顺序排列,每帧:

[dirty_bitmap: ceil(n_tiles/8) 字节]   每 bit 对应一个 tile,置位=该 tile 本帧变化
[packed_indices]                       所有脏 tile 的调色板索引,按 tile 行主序拼接,
                                        再按 index_bits(1/4/8)打包;本帧内字节对齐

要点:脏块位图被放进压缩流内部(bitmap-in-stream)。位图高度稀疏且规整,与索引流一起熵编码后开销极小——这是相对"位图未压缩独立存储"的关键优化,尤其利于大画布素材。

3.7 JPEG 段负载(method = 1)

[u16 x][u16 y][u16 w][u16 h]   脏区包围盒(w、h 按 8 对齐,适配 JPEG 8×8 块)
[baseline JPEG 字节]

3.8 关键帧与 replace 语义

  • 第 0 帧所有 tile 均为脏(整屏铺底);播放起点/切换新表情时第一帧自然重绘整个背景。
  • replace 语义:段负载记录的是脏区新像素(不是差值),写入即覆盖;未变区域的保持由显示侧负责(见 §5.4)。故解码不需要保留上一帧用于叠加。

4. 编码流程(详细)

输入:GIF 文件(当前编码器仅支持 GIF 源;其他格式作为后续扩展)。

编码分七步。

步骤 1 — GIF 解码与合成

逐帧 LZW 解码,按 disposal 规则合成为不透明 RGB 帧序列(合成掉透明/背景层,避免设备端再合成)。

技术:标准 GIF/LZW 解码 + disposal 合成。这是唯一与源格式相关的步骤,后续步骤与源无关。

步骤 2 — 全局调色板量化与位深选择

统计整个帧序列的精确颜色(RGB565 域)。 - 若唯一色数 ≤ 256:建立精确全局调色板,每像素映射为索引——无损; - 若 > 256(写实素材):中位切分量化到 256 色(有损),或转入 JPEG 路径。 按色数选 index_bits:≤2→1,≤16→4,≤256→8。

选型:全局调色板 vs GIF 的每帧局部调色板——全局只存一次,省去逐帧重复;位深自适应把索引数据按色数压到理论最小(2 色仅 1bit/像素)。

步骤 3 — 自适应 tile 尺寸扫描

对候选 tile 尺寸集合(如 8/16/32/64)分别执行步骤 4–7 的完整编码,比较最终文件大小,选最小者,并把选定的 tile_w/tile_h 写入文件头。

选型:固定 tile 无法兼顾"变化集中的小画布"(宜小 tile,脏块贴合)与"少色大画布"(宜大 tile,压低位图开销)。自适应扫描以离线时间换最优体积。

步骤 4 — 逐帧脏块检测

对每帧,按 tile 网格与前一帧逐 tile 比对(第 0 帧全脏),生成脏块位图;记录脏 tile 的像素与整体包围盒。

选型:块级差分 vs EAF 的整帧分条带——块级可离散跳过多处分离的变化,不重解未变背景。

步骤 5 — 逐帧编码方式判定(调色板 vs JPEG)

对每帧计算两个候选的压缩后大小: - 候选 A(调色板):脏 tile 索引按位深打包后,用 best-of(heatshrink, deflate)压缩; - 候选 B(JPEG):脏区包围盒像素编码为 baseline JPEG。 取较小者作为该帧的编码方式。

选型:表情帧候选 A 远小,写实帧候选 B 远小;逐帧判定使单一容器兼容两类内容。实测表情素材全部选中 A,写实素材几乎全选 B。

步骤 6 — 成段与压缩

把连续的调色板帧分组为段(每段至多 SEG 帧,默认 16);JPEG 帧各自成段。 对每个调色板段:按 §3.6 拼出"逐帧(位图 + 打包索引)"的原始 blob,整段用 best-of(heatshrink, deflate)压缩为一条流。

选型:多帧共享一条压缩流,吃跨帧冗余(循环/重复动作),并摊薄每帧独立压缩头。SEG 越大压缩越好、解码 scratch 越大——是体积/内存的可调旋钮。

步骤 7 — 写文件

写文件头 + 全局调色板 + 各段负载 + 段表。

编码伪代码(简化):

best = ∞
for TW in {8,16,32,64}:
    size = encode_with_tile(TW)      # 步骤 4-7,返回文件大小
    if size < best: best, bestTW = size, TW
emit encode_with_tile(bestTW) 到 .tef

encode_with_tile(TW):
    for each frame i: classify(i) → 调色板 or JPEG   # 步骤 5
    group 连续调色板帧为段(≤SEG),JPEG 帧独立成段    # 步骤 6
    for each 调色板段:
        blob = concat over frames { dirty_bitmap(i) + packbits(dirty_indices(i)) }
        payload = best_of_compress(blob)             # heatshrink / deflate
    for each JPEG 段:
        payload = [x,y,w,h] + jpeg(bbox_pixels)
    写 header + palette + payloads + seg_table

5. 解码流程(详细)

输出:可直接经 SPI / QSPI / RGB 等接口刷到屏幕的像素数据(RGB565 / RGB888)。

步骤 1 — 解析与预处理(开播一次)

读文件头,校验 magic/version;载入全局调色板并一次性预转成屏幕字节序的 RGB565/888,缓存为 LUT;读段表。

选型:调色板预转缓存一次,使后续逐像素上色退化为一次数组查表(O(1)),避免逐像素现算。

步骤 2 — 按段解码

遍历段表。对每个段:

若为调色板段(method = 0): 1. 用段的 comp 指定的解码器(heatshrink / deflate)整段解压为 blob; 2. 按帧遍历(frame_count 帧),每帧: a. 从 blob 读 ceil(n_tiles/8) 字节脏块位图; b. 依位图统计本帧脏 tile 及脏像素总数,据 index_bits 算出打包字节数,读取并位解包为 8bit 索引; c. 对每个脏 tile:索引经调色板 LUT → RGB565,得到该 tile 像素; d. 将各脏 tile 输出到屏(见 §5.4)。

若为 JPEG 段(method = 1): 1. 读 [x,y,w,h]; 2. 用硬件或软件 JPEG 解码器解码脏矩形 → RGB565; 3. 将脏矩形输出到屏。

步骤 3 — 帧调度

按 fps(或后续扩展的逐帧时长)调度下一帧的输出时刻。

步骤 4 — 输出到屏:两种刷屏模式(是否支持 GRAM)

TEF 差分为 replace 语义,"未变区域如何保持"取决于屏是否自带显存(GRAM),解码器支持二选一:

模式 A — 屏幕自带 GRAM(局部刷新): 适用于带 GRAM 的控制器(多数 SPI/QSPI LCD)。只输出脏区:设地址窗口 CASET/RASET = [x, x+w-1] / [y, y+h-1],RAMWR 后 DMA 推送脏区像素。未变区域由面板 GRAM 自动保持,MCU 侧无需整帧缓冲。

模式 B — 屏幕无 GRAM(解码器自缓存): 适用于需持续扫描输出的接口(如 RGB 并口 LCD)。解码器在内存中自维护一块 canvas_w × canvas_h × bpp 的整帧缓冲("自缓存 GRAM"),每帧把脏区结果写入其对应位置,由显示控制器持续扫描该缓冲。此模式需额外整帧缓冲,但解码工作量仍只涉及脏区,CPU 优势不变。

两模式共用同一 .tef 与同一套解码逻辑,仅"输出目标"不同。

解码伪代码(简化):

LUT = 预转调色板到 RGB565
for seg in 段表:
    if seg.method == 调色板:
        blob = decompress[seg.comp](seg.payload)
        p = 0
        repeat seg.frame_count 次:
            bitmap = blob[p : p+ceil(n_tiles/8)]; p += ceil(n_tiles/8)
            dpx = 统计脏像素; pkb = 按位深算打包字节
            idx = unpack_bits(blob[p : p+pkb], index_bits); p += pkb
            for 每个脏 tile: 像素 = LUT[idx...]; 输出该 tile
    else: # JPEG 段
        (x,y,w,h) = seg 头; 像素 = jpeg_decode(seg.jpeg); 输出该矩形
    输出 = 模式A(设窗口+DMA) 或 模式B(写自缓存缓冲)

7.3 CPU:每次播放需解码产出的像素量(占"整帧 × 全帧数"的比例)

素材 GIF EAF TEF
黑白 smile LZW 全子图 100% 4%
卡通 LZW 全子图 100% 5%
彩色眼睛 LZW 全子图 100% 12–27%
写实开场 LZW 全子图 100% 42%(JPEG,可硬解)
  • EAF 每帧重画整帧,恒 100%;
  • TEF 只解码脏 tile,表情类仅 4%–27%;
  • GIF 虽也只解码文件自带子图,但 LZW 逐符号串行、需维护字典,单像素成本高于 TEF 的"解包 + 查表";写实帧走硬件 JPEG 时 CPU 近乎为零。

7.4 RAM:解码工作内存(320×240、RGB565、deflate 示例)

方案 峰值工作内存 需整帧 framebuffer
GIF ~245 KB(150K 画布 + 75K 索引画布 + 20K LZW 表) 强制
EAF ~42 KB(10K 条带 + 32K deflate) 无
TEF 模式 A(有 GRAM) ~35 KB(32K deflate 窗口 + tile/段 scratch + LUT) 无
TEF 模式 B(无 GRAM) ~185 KB(模式 A + 150K 自缓存整帧) 自缓存
  • 有 GRAM 时,TEF 工作内存最低且无整帧缓冲(约为 GIF 的 1/7);
  • 无 GRAM 时需自缓存整帧,但仍省去 GIF 的索引画布与 LZW 表,且解码只碰脏区;
  • 段长 SEG 控制段解压 scratch 大小,可按内存预算调整。

8. 适用边界与已知局限

最适合 TEF 的素材:少色到中等色数、静止背景 + 局部动作的表情动画——存储显著小于 GIF(实测全库 0.29×~0.44×)、无损、CPU/RAM/带宽全面领先。

已知局限:

  1. 写实/噪点内容:调色板压不动,需走 JPEG 路径,存储仍高于 GIF(约 1.30×);此类内容更适合视频编码,JPEG 帧为有损。
  2. 随机定位:差分帧需从最近关键帧顺序重放;当前每段首帧非强制关键帧,如需频繁跳帧应提高关键帧密度。
  3. 编码耗时:自适应 tile 扫描 + 逐帧 best-of(两种熵编码 + JPEG 试编)增加离线编码时间;不影响运行时。
  4. 段解压内存:模式 A 下段越长,解压 scratch 越大;由 SEG 调节。
  5. 输入格式:编码器当前仅支持 GIF 源。

附录:参考实现

规范配套一套可编译的参考实现(编码器 + 解码器 + 校验)。编码器实现自适应 tile 扫描、多帧成段、位图并入流、1/4/8bit 调色板 best-of(heatshrink/deflate)与 JPEG 帧;解码器实现两种刷屏模式的回放与逐像素/PSNR 校验。移植到具体平台时,仅需实现"输出到屏"(设窗口 + DMA,或写入自缓存缓冲)与可选的硬件 JPEG 解码接口,核心解码逻辑与平台无关。
