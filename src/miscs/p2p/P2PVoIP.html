2.信令协议(MQTT 308 RTC)

涂鸦 MQTT 自定义协议号 308,SS190 兼容 JSON。呼叫报文:

展开设备 / APP 呼叫 JSON 示例

呼叫设备:

channelType:0=音频,1=视频,2=音视频。timeout 必须是数字型毫秒时间戳。

{"type":"rtc","data":{
  "event":"call",
  "curId":"<本机devId>",
  "targetId":"<对端devId>",
  "sessionId":"<devId+6位随机字符>",
  "timeout":1893456180000,
  "extra":{"channelType":0,"category":"dgnzk"}
}}

呼叫 APP(目标 key_ 前缀 + callType:3):

{"type":"rtc","data":{
  "event":"call","callType":3,
  "curId":"<本机devId>",
  "targetId":"key_1",
  "sessionId":"<devId+6位随机字符>",
  "timeout":1893456180000,
  "extra":{"channelType":0,
           "category":"dgnzk",
           "bizType":"dgnzk"}
}}

上述 timeout 仅是保持 JSON 可复制解析的数字示例;实际由代码计算为“当前 POSIX 毫秒时间戳 + 呼叫超时”,不应照抄示例值发送。

展开全部信令事件与 control 映射
信令事件方向含义 → control 上抛事件
call收来电 → EVT_INCOMING(解析 channelType/targetId/targetLocalKey/targetName,同 timeout 去重);自动回 ring
ring收/发对端已振铃 → EVT_RINGING
answer收/发接听 → EVT_ACCEPTED(主叫侧);发送侧进 ACCEPTED 并启心跳
already_answered收他端已接听 → EVT_ACCEPTED_BY_OTHERS
reject / busy收/发拒接 / 忙线 → EVT_REJECT / EVT_BUSY
cancel收/发主叫接通前取消 → EVT_CANCEL
not_answered收/发超时未接 → EVT_UNANSWERED
hang_up收/发通话中挂断 → EVT_HANGUP
stop收/发异常终止 → EVT_STOP(reason=busy 转 EVT_BUSY)
heartbeat收/发保活:收即回包并刷新计时;30s 无心跳 → EVT_ERROR
要点:呼叫超时默认 180s(manager 传入,control 内部默认 30s);sessionId=devId+6 位随机;设备上线报一次 {"metas":{"rtcCapability":7}}(声明音视频对讲能力,APP 据此展示入口)。

5.2 预览式直接拉流(不走呼叫信令)

无 call/answer 信令:manager 呼叫状态保持 IDLE,音频和视频事件职责不同。AUDIO_START 会执行 enter_call()、将适配层置为 INCALL 并发布 UI 事件;AUDIO_STOP 会执行 leave_call()、回到 IDLE 并通知 UI。VIDEO_START/VIDEO_STOP 只负责切换 P2P 模式和订阅/退订 H264,不改变适配层状态,也不推送呼叫页。麦克风直送仅由 AUDIO_START 建立的 INCALL 状态放行;manager 内补置的 enable_send_audio 不参与这条直送路径。
当前时序约束:音视频同时预览时,VIDEO_STOP 会执行 leave_call(),但适配层可能仍是 INCALL,直到 AUDIO_STOP 才收敛为 IDLE。排查“状态显示在通话中但已退出 P2P 模式”时,应优先核对 VIDEO_STOP 与 AUDIO_STOP 的到达顺序。

展开上行缓冲、门控与时间戳细节
  • 逐帧即时直送,不经 manager jitter 缓冲:manager 另有 240ms jitter + 40ms 绝对节拍匀速发送线程(为设备↔设备平滑而设,会抬高延迟),当前适配层选择直送,与原生方案一致。匀速线程用绝对时刻锚点防长通话漂移;落后超一帧丢欠债重新对齐。
  • G.711U(≈8KB/s)比 16bit PCM(16KB/s)带宽减半;发送环形缓冲 max_buffer_seconds=0,拥塞即丢旧帧控延迟。
  • 当前生效门控只有适配层通话状态:tuya_toy_tmm_voip_audio_feed() 仅检查 is_incall(),随后直接调用 tuya_tmm_stream_audio_send()。manager 的 send_audio_enable + stream_conf.enable_send_audio 双重门控、call_mic_change 静音以及连续 400ms 欠载检测只服务于 tuya_tmm_manager_data_feed() + 匀速发送线程;当前工程没有调用这条备用上行路径。
  • 时间戳基准目前不一致:音频直送使用 POSIX 墙钟,视频使用 P2P SDK 单调时钟。发生 NTP 校时时可能产生跳变;需要排查 A/V 同步时应优先检查并统一时间基准。

展开 UI 服务实现细节
  • 线程模型:EVENT_TOY_VOIP_UI/呼出超时/stream-ready 均在非 UI 线程;一律经 ui_app_async_call() 封送 UI 线程后才更新状态/回调页面(可直接操作 LVGL)。
  • 前台保证:INCOMING/IN_CALL 到来时若不在呼叫页,自动 ui_route_push(UI_PAGE_CALL)。
  • 呼出超时:dial/dial_device 后启 30s 延迟任务,超时主动 hangup + FAILED。
  • 运行时开关(兼 TMM 栈启动闸门):P2P 开关默认 OFF(KV 由 ui_svc_dev_ctrl 持久化)。OFF→栈不存在(零线程/零信令,APP 呼叫无响应);ON→ui_svc_call_init() 订阅事件后调 tuya_toy_tmm_voip_start() 现场启动,即时生效(单向,关闭需重启回收)。「自动接听」同样 UI 层持有+KV 持久化。
  • 联系人拉取契约:异步工作项直接调用 ATOP contact.sync + contact.list,不等待 stream-ready;count≥0=成功(0=确实无设备),count<0=失败(可重试)。EVENT_TMM_STREAM_READY 仅作为栈启动后的自愈刷新触发;in-flight 请求合并;回调单槽,页面 on_destroy 传 NULL 注销。
  • 摄像头限制:当前 UI 服务在摄像头不可用时会拒绝所有来电(包括纯语音来电),并禁止手动接听;呼出语音路径没有同等检查。因此「无相机仅降级为语音」并不是当前来电侧的实际行为。

13.运行约束与排障要点

本章仅汇总当前源码可直接验证的行为。函数名、状态名和配置项可作为代码检索入口;实现变更时应同步更新本章。

13.1 启动与资源约束

🧩
RESOURCE

媒体框架是单例

TMM 与原生 IPC P2P 路径只能启动一个。

当前使用 TMM禁止双初始化
代码入口

ui_svc_call_init() → tuya_toy_tmm_voip_start();当前不调用 tuya_p2p_app_start()。

🎚️
RUNTIME GATE

开关决定设备是否可呼

OFF 时没有通话栈和 MQTT 308 回调;ON 时现场启动。

OFF = 不可达关闭后重启回收
时序细节

rtcCapability 延后到首次启动上报。若 MQTT 已连接,tuya_tmm_stream_init() 通过 get_mqc_conn_stat() 补偿连接事件。

13.2 会话状态与结束处理

✅
ACCEPT

接听即进入通话

收到 ACCEPTED 或本机 answer 后立即切 P2P,不等待 AUDIO_START。

原因与幂等

避免设备间双方等待对方先拉流;重复进入事件由适配层状态检查忽略。

📷
KNOWN LIMIT

无相机拒绝全部来电

当前纯语音来电也会被拒绝;主动呼出语音不受限制。

检查位置

INCOMING 和手动接听均调用 ui_svc_camera_available();返回 false 时直接拒接。

🏁
TERMINAL

终局统一回到 IDLE

拒接、忙线、取消、未接、挂断、停止和错误共用退出路径。

清理顺序

__voip_leave_call() 先兜底退订 H264,再切回 CHAT;页面离开时也会挂断活动通话。

13.3 媒体链路注意事项

🎙️
UPLINK

音频由适配层直送

16K PCM → 8K G.711U 后直接送入 stream。

实际门控

audio_feed() 只检查 is_incall()。manager 双重门控、jitter、call_mic_change 和 400ms 告警属于未接入的备用路径。

▶️
PREVIEW

音频驱动状态,视频只管流

预览直拉没有 call / answer;AUDIO 事件更新 INCALL/IDLE,VIDEO 事件不改状态也不推呼叫页。

状态关系

manager 保持 IDLE;AUDIO_START 使适配层进入 INCALL 并放行音频直送。VIDEO_START/STOP early return,仅切模式和启停 H264。音视频并行时需注意 VIDEO_STOP 可早于 AUDIO_STOP 执行 leave_call()。

🕒
TIMESTAMP

音视频时钟不同源

音频使用 POSIX 墙钟,视频使用 SDK 单调时钟。

排查提示

NTP 校时可能造成音频时间戳跳变;排查音画同步或长通话异常时应同时检查两类时间戳。

🩺
SELF-HEAL

麦克风采集自动恢复

通话中发现 wakeup 被迟到回调关闭时重新开启采集。

实现入口

wukong_ai_mode_p2p.on_task 周期检查并修复该状态,用于避免对端偶现无声。

13.4 联系人与超时

👥
CONTACTS

联系人请求不等待媒体就绪

页面立即执行 ATOP contact.sync/list;stream-ready 只用于自愈刷新。

count ≥ 0 成功count < 0 失败
30sUI 呼出等待挂断并显示 FAILED
180sRTC 信令呼叫通常 UI 超时先触发
